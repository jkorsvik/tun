# 33. "What moved since last month"

Half of the reporting a tenant does is a subtraction. Two extracts of the same measure, one
per period, matched on a key, and the reader wants to know what moved, by how much, and
what is new or gone. That work is done by hand in Excel, where the arithmetic is invisible,
the result dies with the spreadsheet, and nobody can see afterwards whether a key was
dropped on the way.

This example is that subtraction as an artefact: one self-contained file, every key in it,
the change beside each one.

```bash
python3 examples/33-comparison/generate_data.py

python3 tools/build_comparison.py \
  --before examples/33-comparison/forrige.csv \
  --after  examples/33-comparison/denne.csv \
  --key Region --value Omsetning \
  --title "Omsetning per region: september mot oktober" \
  --before-label September --after-label Oktober --meaning up \
  --source "Syntetisk eksempeldata (forrige.csv, denne.csv)" \
  --requested-by Innsikt \
  --out examples/33-comparison/sammenligning.html \
  --annotate
```

`--annotate` adds the review layer, so a reader who disagrees with a row can click it and hand
back one text block ([`docs/31`](../../docs/31-review-roundtrip.md)). A key that exists on one
side only carries `status: gone` or `status: added` in the block, so the report says why its
figure is empty rather than calling the row wrong. Without the flag the file is what it was.

Then verify it the way a recipient would open it:

```bash
uv run --extra verify python3 tests/test_comparison_dashboard.py --engines chromium,webkit
uv run --extra verify python3 tools/verify_viewports.py examples/33-comparison/sammenligning.html
uv run --extra verify python3 tools/verify_a11y.py examples/33-comparison/sammenligning.html
uv run --extra verify python3 tests/test_review_comparison.py
```

## The five rules it carries

* **A key is summed, not read once.** `forrige.csv` has 11 rows for 6 regions. Taking the
  first row per key answers a different question, and the answer it gives is plausible,
  which is worse than wrong. The builder sums, and the suite checks the sums against
  arithmetic it does itself.
* **A key in only one extract is named, never dropped.** `Nordvest` stops reporting and
  `Sørvest` starts. A region that stopped reporting and a region with zero sales produce
  the same number and are not the same fact, so the page says "borte" and "ny" in words.
* **A percentage needs a denominator.** A key that went from 0 to 5 has a real change and
  no meaningful percent. The page shows a dash rather than a fabricated 100 %.
* **The no-JS view is the largest movers, pre-drawn.** Twelve rows, the totals, and the
  sentence that says search and sorting need the script. A reader whose browser will not
  run scripts sees the answer, not an empty table.
* **A key is text.** A key holding `</script>` cannot end the script element: the payload
  is escaped at `<`, `>` and `&`, and a hostile key is a check in the suite. A CSV cell once
  ran script in this repository.

## Colour is a verdict only when you say so

An increase is not good news by itself. More revenue and more overtime are the same
arithmetic. So the default build colours both directions the same and lets the sign and the
words carry the movement. `--meaning up` or `--meaning down` says which direction is good
news, and only then do the approved status colours apply: Success Green `#007b5e` for good,
Fire Red `#dc2a2a` for bad, both from `tools/tokens/status-semantic.css` and both measured
at WCAG AA on white.

The sign is always there, per WCAG 1.4.1: colour is never the only signal. The suite
measures the computed colours in a browser, so a colour recalled from memory instead of read
from the token file fails a check rather than shipping.

## When to use this instead of a dashboard

Use it when the question is "what changed", and the answer is a table of keys with two
numbers each. Use `tun-new` when the question is "how does it look across regions and
months", and `build_register.py` when the question is "give me the list itself". A
comparison of two aggregates is not a dashboard with two dates stapled on: the interesting
column is the difference, and it should be a column.

## What this example is not

It does not reconcile the two extracts. If the same key has a different meaning in the two
files (a redefined region, a channel that moved in or out), the page will report the change
faithfully and be wrong about the cause. That is a question for whoever produced the
extracts, and the provenance block names them.

Every number here is invented. The files carry no data from any engagement: `forrige.csv`
and `denne.csv` are generated by `generate_data.py`, and the numbers add up to nothing.
