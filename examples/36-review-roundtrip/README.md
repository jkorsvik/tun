# 36. The file that answers back

Every other artefact in this repository is one-way. Someone opens it, disagrees with a
number, and the only route back is a screenshot and a sentence naming neither the row nor
the build: *"tallet for mars ser feil ut"*, when the file holds 96 rows and three builds
exist. Here the file asks. The reader presses one button, clicks the row, writes a comment,
and copies a single text block. On the other side a tool reads the block, finds the row
again, and puts the file's own number next to the reader's.

```bash
python3 examples/36-review-roundtrip/build_example.py
```

That one command writes all four files: the data, the annotated artefact, the block a
reader would paste back, and the report that block produces. `SOURCE_DATE_EPOCH` pins both
stamps, so running it twice gives the same bytes and the committed report stays true.

To read a block yourself, from a file or straight off the clipboard:

```bash
python3 tools/read_review.py examples/36-review-roundtrip/saksbehandling.html \
    examples/36-review-roundtrip/tilbakemelding.txt

pbpaste | python3 tools/read_review.py saksbehandling.html -
```

Then open it the way the recipient does, and measure it:

```bash
uv run --extra verify python tests/test_review_roundtrip.py
uv run --extra verify python tools/verify_dashboard.py examples/36-review-roundtrip/saksbehandling.html
uv run --extra verify python tools/verify_viewports.py examples/36-review-roundtrip/saksbehandling.html
uv run --extra verify python tools/verify_a11y.py examples/36-review-roundtrip/saksbehandling.html
```

## The four things it proves

* **A row has a name that survives a rebuild.** `keys: Maaned, Enhet, Sakstype, Kanal` is
  the four categorical columns, and nothing else. The measure is deliberately not part of
  it: if the figure changes, the comment must still find its row. In this data those four
  are unique per row; where a source file holds real duplicates the report says how many
  rows share the name rather than guessing.
* **The block carries what the reader saw.** `value: 79 200` is the reader's figure, and the
  report shows `83 160` beside it. Neither is declared wrong: the file holds one number, the
  reader holds another, and only a person can say which is the invoice and which is the
  extract.
* **A row the file does not hold is a finding, not a crash.** The third comment names
  `Enhet Øst`, which this file does not have. The report says so, keeps the comment, and
  counts it.
* **A pasted mail survives.** The committed `tilbakemelding.txt` is a real-shaped message:
  a greeting, every block line quoted with `>`, one comment wrapped onto a second line by
  the mail client, and a signature. All of it parses. What the parser did not use is listed
  under `notes from the block`, so a comment is never silently dropped.

## Look at it, do not trust the number

The browser half of the suite is not a formality. It opens the file from `file://` in
Chromium, presses **Kommenter**, clicks a row, types, adds, and hands the block Chromium
produced to the parser, then requires the row it clicked to resolve. A layer nobody has
clicked is a layer that does not work, and a report that agrees with a hand-written fixture
proves only that the fixture and the parser share an assumption.

With scripting off, the same section is a sheet of text: the identity, the column order and
three of the reader's own rows filled in, with a blank comment line under each. That is why
the block is `key: value` lines and not JSON.

The layer is off unless `--annotate` is passed. Without it the artefact keeps its old bytes,
and the suite asserts that too.

Data and artefact are synthetic (`saksbehandling.csv`, generated by `build_example.py`).
Nothing here comes from a real case.
