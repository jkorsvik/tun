# Working with real sources

**Reader:** user — you want an artefact out of your own data and do not intend to change the toolkit.

Methods from two real deliveries built on Tún, written down so the next one starts
from them. The cases themselves stay private. Only the methods are here.

- **Case 1** (2026-09-28): a day overview for a school with an adapted programme. The source
  was the school's own spreadsheet, edited by one person every day.
- **Case 2** (2026-09-29): a report from a survey among companies in one industry. The
  source was a form-tool export, plus facts gathered from public web pages.

Tooling that automates these methods is an open issue. This document describes the
methods only.

## Understand the source before you build

**Ask the owner. Do not infer.** In case 1, a code table, an override sheet, two extra
states and a rule for moved staff were all built from guesses about what the cells meant.
The owner's one-line answer ("every code means absence") removed a fifth of the reader.
When the owner can answer a semantic question in one sentence, ask it before you build an
interpretation layer. Ship the simplest reading while you wait.

**Build the step the real workflow depends on first.** In case 1 the transport view was
built first, because it looked central. The real order was absence, then staffing, then
transport. Transport was the last step and depended on the other two. Map the real
dependency chain with the people who run it before you choose what to build first.

**Copy the structure, never the rows.** Take the source's sheet names, column names and
vocabulary into a reusable description. Leave every real value out. The synthetic example
then looks familiar to its users and holds nothing real. `examples/17` was built this way.

**Let the artefact carry the routine.** A dashboard for a daily routine can also be the
written description of that routine: who updates what, when, and what to do when a value
is missing. In case 1 the routine existed only in one person's head. The delivered page
became the first written version of it.

## Reading the data

**Form-tool CSV exports are fragile.** Decode with BOM awareness and detect the dialect
(separator, quoting). Do not assume UTF-8 without a BOM, or a comma separator. Deduplicate
by the stable respondent ID, never by the display name. Keep a small alias file for name
variants of the same organisation.

**Excel cached values can be stale.** `openpyxl` with `data_only=True` reads the value
that Excel cached at the last save. If the workbook was not recalculated before it was
saved (for example, it was generated by another tool), the cached value can be wrong or
missing. Check a few formula cells against a fresh recalculation, or recalculate first.

**Keep manual corrections in a side file.** A correction made by phone (in case 2, a
distance typed as 14,200 km was really 375 km) must survive the next re-run of the
pipeline. Store each correction as a row with the value, the source and the date, and
apply it after cleaning. A correction made directly in the generated output is lost on
the next build.

**Primary answers beat secondary sources.** A respondent's own answer has higher fidelity
than a public web page. Secondary sources may fill empty fields only. They never overwrite
an answer that already exists.

## Facts gathered from the web

In case 2, three research agents returned 70 claims, each with a "verbatim" quote. 40 of
the quotes were not on the cited page. Some were numbers copied from the agents' own task
text. A confident quote costs nothing to produce.

The gate is mechanical:

1. Fetch every cited URL yourself and keep the text.
2. Accept a claim only if its quote is an exact substring of that text.
3. Re-check on every import, not once.

All 70 claims were rejected and the research was redone under the gate.

## Proving the numbers on the page

A report that aggregates in the browser has two implementations of the same arithmetic:
the build script and the page script. Looking at screenshots does not prove they agree.

- Render the page in a real browser for each filter selection.
- Read every number and every name list from the DOM.
- Compare them with the build script's own aggregation of the same data.
- Inject deliberate bugs into the page script and check that the comparison catches each
  one. In case 2, three injected bugs were all caught. A comparison that cannot fail proves
  nothing.

A release checklist for such a report covered self-containment, file sizes, leftover
placeholders, provenance, stray script text (docs/01 row 25), `:target` navigation (row
24), sticky or fixed headers (row 26), opening the workbook in a second spreadsheet
program, and the key numbers. That is 28 checks in all.
