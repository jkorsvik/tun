# 0001. The folder is the security boundary, never a browser filter

- **Status:** Accepted
- **Date:** 2026-10-10
- **Related docs:** [`docs/00-vision.md`](../00-vision.md), [`docs/02-architecture.md`](../02-architecture.md), [`AGENTS.md`](../../AGENTS.md)

## Context

Every Tier 1 Tún artefact carries its data inside a client-readable `.html` or sibling `data.js` file. Anyone who can open the file can open View Source or DevTools and read every row in it. Teams routinely ask for "one dashboard where each regional manager only sees their own region."

## Decision

Never write a row into a file whose audience should not see it. When different audiences require different rows:

1. Split the source data *before* building.
2. Build one artefact (or one `data.js` in paired mode) per audience.
3. Place each output in its own permissioned folder (SharePoint, OneDrive, or equivalent).

Never implement row-level security as a browser filter, hidden column, or query parameter. When per-viewer filtering cannot be expressed as a small set of folders, route the user to Power BI or a server-enforced backend instead.

## Consequences

- **Positive:** Access control is visible, auditable, and enforced by existing document-store permissions with zero custom auth code.
- **Trade-offs:** High-cardinality per-person views (hundreds of distinct audiences) do not fit Tier 1 files.
- **When to revisit:** Never for client-readable files; this is a physical property of delivering bytes to a reader's device.
